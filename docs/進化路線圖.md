# 年譜處理器（nianpu-processor）進化路線圖

> 定位：把「原始 OCR 文本」升級為「經考據驗證的機器可讀時間數據」的引擎。
> 本文件收錄下一階段 5 個高槓桿進化方向，供後續逐步實施。

## 1. 從「時間層」升到「事件層」（最大的 DH 跳躍）

**現狀**：輸出是「按年切片、帶標題」的文本——時間維度已顯性化，但內容仍是散文。

**目標**：在每年內容上做**事件抽取**，自動標出：
- 事主（who）
- 地點（where）
- 官職／身份（what role）
- 事件類型（科舉、遷轉、喪葬、著述、交遊、征戰…）
- 時間（精確到月／日）

**輸出示意**：

```
### 道光三十年庚戌（1850年）四十五歲
→ {year: 1850, age: 45, events: [
     {type: 升遷, role: 實錄館纂修, place: 京師},
     {type: 喪葬, subject: 道光帝, role: 送梓宮}
   ]}
```

**DH 價值**：有了事件層，年譜才能直接供群體傳記（prosopography）、生涯軌跡統計、交遊網絡分析用——而不需要人再讀一遍。這是把年譜從「可讀文本」變成「可分析資料庫」的關鍵一步。

**可行切入**：LLM 抽取（仿照標點管線 chunk→抽取→merge→verify），或結合既有 slot_model 槽位機制。

## 2. 精確曆法引擎

**現狀**：`REIGN_START_YEARS` 只有「年號元年→公元」，干支換算是近似。

**目標**：內建一個**完整曆法層**：
- 年號起止月／日（不只元年）
- 閏月處理
- 干支逐日精確換算
- 正確的時代界限（如崇禎甲申、清世祖入關等）

**DH 價值**：
- L2 校驗從「能修錯誤」升級到「能精確換算日期」
- 順手修掉 RAG 報告中的詞法誤配類問題（嵗/歲異體、1955/一九五五 數字格式），讓機器對齊統一
- 為事件層提供精確到日的時間戳

## 3. 從「單譜核驗」到「多本互校 + 證據鏈」

**現狀**：文貞公案例已證實有雙 OCR 版本可去重；L2 三錨點只能單譜校驗。

**目標**：正式**校勘模組**：
- 同一人不同版本（稿本／刻本／整理本／OCR 多版）自動並排 diff
- 差異列出供人裁決
- 每個修正標題都記**底本證據**：原字、出處、修正理由

**DH 價值**：讓整理本有學術引用的可追溯性——從「工具輸出」升級為「可被正式引用的整理本」。這是產物能否進入學術引用體系的關鍵。

## 4. 黃金語料 + 回歸測試升級

**現狀**：回歸測試只比「標題數不變」，改動後只驗證覆蓋率不下滑。

**目標**：
- 建立一本（或多本）**人工核驗的黃金年譜**：每個標題的三錨點、公元年、日期都手工確認後鎖為測試基準
- 每次改動不只驗覆蓋率，還驗**正確率**
- 讓自我進化的成長有科學制約，不會默默學壞（配合既有 `--prune` 清理機制）

**DH 價值**：工具長期維護的可靠性基石。沒有正確率基準，擴充格式的同時可能引入隱性錯誤。

## 5. 生態互通

**現狀**：輸出是 Markdown 整理本，來源可對接 CBDB 核驗，屬孤島工具。

**目標**：
- **輸出側**：加 **TEI／JSON-LD／CBDB 匯入格式**
- **地理側**：接 **CHGIS 地名庫**，把「地點」自動轉經緯度 → 行程地圖、空間分析
- **反向**：CBDB 修正後的資料若能回寫，形成雙向校正

**DH 價值**：讓本工具成為 CBDB／CHGIS／Wikidata 生態的「年譜供料端」，而非孤島。互通性是 DH 工具能否被學界採用的決定性因素。

---

## 建議實施優先序

短期性價比最高：

1. **事件層（#1）**——直接提升研究產出
2. **證據鏈（#3）**——讓整理本夠格進入學術引用體系

中期：

3. 精確曆法引擎（#2）
4. 黃金語料與回歸升級（#4）

長期：

5. 生態互通（#5）
