# 年譜智能整理系統設計規格

- 日期：2026-08-08
- 狀態：已確認設計
- 基礎項目：`nianpu-processor`
- 近期定位：以「年份標題智能識別」為核心的本地 Web 應用

## 1. 背景與決策

現有 `nianpu-processor` 已具備年份標題化、年號補全、公元標註、格式預分類、三錨點校驗、CBDB 核驗、語義槽位和自我學習等能力。下一階段不直接建設事件分析、知識圖譜或跨譜問答，而是先將既有規則引擎升級為可觀察、可規劃、可重試、可解釋、可審核的領域智能體。

本設計確認以下產品決策：

1. 第一版做成獨立的本地 Web 應用，本機啟動服務、瀏覽器訪問，未來可部署到服務器。
2. 支持批量導入，但審核與導出以單部年譜為單位。
3. 自主判斷輸入類型、OCR 必要性及文字品質；已有可靠文字時跳過 OCR。
4. 智能核心是陌生年譜的年份標題識別，而不是通用聊天或知識圖譜。
5. 年號、年序、干支、公元年及年齡等可計算錨點，在有多個獨立證據時允許自動修正。
6. 正文 OCR 誤字、缺字、錯行和段落問題只提出建議，保留原文並由使用者確認。
7. 新槽位和新規則先進候選庫，通過回歸測試後才能正式啟用。
8. 第一版預留日記、多來源文獻、事件及實體抽取接口，但不提前實現分析層。

## 2. 產品目標

系統接收一批 PDF、圖片、Markdown 或純文本，為每部材料建立獨立任務，自主完成：

1. 文件與頁面級輸入診斷；
2. 可靠文字取得或必要的 OCR；
3. 年譜格式與傳主推斷；
4. 年份標題候選發現；
5. 全譜時間序列推理；
6. 多錨點校驗及低風險自動修正；
7. 局部 OCR 重試或 LLM 仲裁；
8. 疑點彙總、人工審核和單部導出；
9. 從審核結果生成候選規則並安全驗證。

核心能力定義為：

> 系統能自主學會一部陌生年譜如何標年，結合全文時間序列找全年份標題、排除正文誤標、修正可驗證的紀年錯誤，並解釋每項判斷。

## 3. 第一版範圍

### 3.1 包含

- 批量導入 PDF、圖片、Markdown 和 TXT；
- 原生文本、已有 OCR、純掃描及混合 PDF 分流；
- 頁面級文字品質檢測；
- 版面框、欄位、行序及頁碼映射保存；
- 臨時年份槽位自主歸納；
- 高召回年份候選生成；
- 全譜年號、干支、公元年及年齡序列推理；
- 傳主推斷及 CBDB 生卒年輔助驗證；
- 可計算紀年錯誤自動修正；
- 正文 OCR 及版面問題的修正建議；
- 局部重新 OCR、重新分析和明確停止條件；
- 批量任務中心及單部年譜審核工作區；
- 自然語言任務指令；
- 修改日誌、撤銷、重新運行及單部導出；
- 候選規則、回歸驗證、版本管理和回退。

### 3.2 不包含

- 事件、人物、官職、著作和地點的正式抽取管線；
- 知識圖譜；
- RAG 問答；
- 跨譜比較分析及報告生成；
- 原生桌面安裝包；
- 多租戶、計費和複雜權限；
- LLM 自由改寫正文；
- LLM 生成正則後直接投入正式規則庫。

## 4. 設計原則

1. **原始證據不可覆寫**：掃描頁、原始 OCR、原始文本及版面位置永久保留。
2. **確定性工具優先**：OCR、格式解析、年號換算、干支計算和序列驗證由可測試工具完成。
3. **LLM 僅處理語義歧義**：用於槽位歸納、局部仲裁、解釋和自然語言命令解析。
4. **全譜優先於單行**：年份標題判斷以全局序列自洽為主要證據，不逐行貪心決定。
5. **自動修改必須可證明**：至少兩個獨立錨點支持，且不得與更高可信證據衝突。
6. **正文保持克制**：正文問題只生成建議，未經確認不修改整理稿。
7. **所有決策可追溯**：保存原值、建議值、證據、置信度、工具版本和操作者。
8. **學習先進沙箱**：任務臨時配置與候選規則不得直接污染正式能力。
9. **批量處理、單部負責**：批量層只管理任務，審核和導出在單部工作區完成。
10. **為未來預留穩定接口，不提前建設空功能**。

## 5. 總體架構

```text
Web 前端
  ├─ 批量任務中心
  ├─ 單部年譜工作區
  ├─ 年份時間線與疑點中心
  └─ 自然語言指令框

Python 應用服務
  ├─ 任務編排器
  ├─ 文件診斷器
  ├─ OCR 適配器
  ├─ 時間標題智能引擎
  │    ├─ 年份候選生成器
  │    ├─ 臨時槽位歸納器
  │    ├─ 全譜序列求解器
  │    └─ 局部 LLM 仲裁器
  ├─ 多證據校驗器
  ├─ 審核與修正服務
  ├─ 候選規則及回歸服務
  └─ 導出器

儲存
  ├─ SQLite：任務、頁面、候選、決策、修正及規則
  └─ 文件工作區：原件、頁面圖、OCR、整理稿及報告
```

第一版採用模組化單體架構。後端保持 Python，以 HTTP API 對前端提供任務和審核能力；前端採用獨立 TypeScript Web 界面。第一版使用 SQLite 和本地文件，不引入 Redis、Celery 或分佈式微服務。部署階段可以替換任務隊列、文件儲存和身份驗證，而不改變領域引擎接口。

## 6. 智能體運行模型

每部年譜有獨立狀態，按照受控狀態機運行：

```text
已導入
→ 文件診斷
→ 文字取得／OCR
→ 格式分析
→ 標題候選生成
→ 全譜序列求解
→ 紀年校驗
→ 局部重試或仲裁
→ 待審核
→ 已確認
→ 已導出
```

任務編排器執行「觀察—規劃—行動—校驗—反思」循環，但可選行動限制為明確工具集合：跳過 OCR、全文 OCR、局部 OCR、切換臨時槽位、重新生成候選、重新求解序列、局部仲裁、提交人工或完成。不得讓 LLM 生成任意代碼或直接重寫全文。

每輪決策輸出結構化記錄：

```json
{
  "action": "correct_chronology",
  "original": "康熙十四年乙未",
  "replacement": "康熙五十四年乙未",
  "evidence": [
    "乙未對應1715年",
    "傳主本年六十五歲，推定出生年1651",
    "前後條目分別為康熙五十三年、五十五年"
  ],
  "confidence": 0.99,
  "risk": "low",
  "auto_apply": true,
  "explanation": "年號年序與三個獨立錨點衝突，判定十位數漏刻。"
}
```

## 7. OCR 與文字品質診斷

### 7.1 頁面級分流

每頁判斷：

- 是否有文字層；
- 文字層是否可讀；
- 是否為掃描、原生文本或混合頁；
- 是否為橫排、豎排、雙欄或多欄；
- 行序是否混亂；
- 年號、干支及中文數字等關鍵字符異常率；
- 現有 OCR 是否足以進入整理。

可靠文字直接提取；低品質或無文字頁進 OCR；混合 PDF 逐頁選擇。已有文字層不等於可用文字，亂碼、錯序或關鍵字符損壞仍可觸發重做。

### 7.2 OCR 中間結果

除純文本外，保存頁碼、文本塊、行、邊界框、閱讀順序、OCR 置信度及頁面圖片引用。年份識別器可據此重建被拆成多行或多欄的標題。

### 7.3 反向重試

首輪標題識別後生成診斷：確認標題、疑似漏標、疑似誤標、干支或年齡斷裂，以及相關低品質頁面。若疑點集中於低品質區域，編排器可裁切標題區域重識別或更換 OCR／版面參數，然後重新求解年份序列。

停止條件：

- 同一頁最多重新 OCR 兩次；
- 新一輪未提高標題序列一致性時停止；
- 高風險正文問題不得因重試自動改寫；
- 仍無法確定的項目進人工核對；
- 已確認標題不因低可信 LLM 建議而自動回退。

## 8. 年份標題智能引擎

### 8.1 候選發現

第一輪以高召回為目標，綜合年號、年序、干支、公元年、民國年、年齡、人物前綴、出生或卒年詞、獨立短行、縮進、版面位置及重複結構生成候選。候選生成不直接修改文本。

### 8.2 臨時槽位歸納

分析卷首和前若干個高可信候選，生成本次任務專用配置，例如：

```json
{
  "year_style": "reign_sequence",
  "reign_optional": true,
  "ganzhi_required": true,
  "person_prefix": "先生",
  "age_connector": "年",
  "age_suffix": "嵗",
  "cross_line": true
}
```

臨時槽位只在當前任務使用。經使用者審核及回歸驗證後，才可成為正式模板。

### 8.3 全譜序列求解

候選按整本書共同求解，而非逐行決定。計分因素包括：

- 干支逐年推進；
- 年齡通常逐年加一；
- 公元年連續或合理跳躍；
- 年號年遞增及改元；
- 相鄰標題結構一致；
- 出生、卒年與 CBDB 範圍；
- 候選在版面和篇章中的位置；
- 正文引用、序跋落款、註文和科舉小注等負向特徵。

求解結果只有三類：確認標題、排除、待核。所有結果保留分數及證據。

### 8.4 局部 LLM 仲裁

只有規則和序列仍無法判斷時，才向 LLM 提供候選行、前後正文、相鄰年份、臨時槽位及錨點計算。LLM 只可輸出「標題、非標題、待人工」及理由，不直接改全文。

## 9. 修改權限與證據政策

### 9.1 可自動修正

年號、年序、干支、公元年及年齡等紀年字段，在至少兩個獨立錨點支持且沒有更高可信衝突時可自動修正。修正後必須重新運行序列和錨點檢查。

### 9.2 必須人工確認

- 正文 OCR 誤字、缺字和衍字；
- 錯行、錯欄及段落重排；
- 原文語義改寫；
- 只有單一證據支持的紀年推測；
- 稿本筆誤與史實矛盾無法區分的情況。

### 9.3 原文與整理稿

標題可保存計算修正值，但原始 OCR 和圖像不得覆寫。推定字符必須標明來源是序列推理，而非圖像清晰識別。

## 10. 使用者界面

### 10.1 批量任務中心

顯示每部材料的文件類型、頁數、OCR 決策、當前階段、確認標題數、自動修正數、待核數、失敗原因及審核入口。批量層提供啟動、暫停和重試，不混合審核不同年譜。

### 10.2 單部年譜工作區

包含五個視圖：

1. 原始材料：PDF 頁面、OCR 文本和版面框聯動；
2. 年份時間線：按公元年排列標題，顯示改元、跳年及序列衝突；
3. 疑點中心：漏標、誤標、紀年衝突、低品質 OCR 和正文建議；
4. 修正對照：原文、整理結果、證據、理由、接受、拒絕和撤銷；
5. 導出：Markdown、校訂報告、修正日誌、時間單元 JSON 和原始 OCR。

### 10.3 自然語言命令

支持「重新檢查出生條目」「只看低置信度標題」「重新 OCR 第十七頁第二欄」「檢查萬曆年間是否漏標」「解釋某項修正」和「撤銷本輪修正」等指令。

自然語言先轉為結構化命令。會改變結果的命令顯示影響範圍；正文修改仍須人工確認。所有命令寫入任務日誌。

## 11. 受控學習

### 11.1 規則類型

- OCR 字形修正；
- 年號、干支及年齡正規化；
- 年份標題槽位配置；
- 傳主稱謂和年齡前綴；
- 跨行、豎排及欄位合併模式；
- 正文引用和序跋落款排除規則；
- 單書特例。

單書特例不得自動升級為全局規則。

### 11.2 生命週期

```text
任務臨時配置
→ 候選規則
→ 回歸測試
→ 已驗證規則
→ 正式啟用
→ 降級或停用
```

每條候選保存來源書、原因、正例、反例、建立來源、適用範圍、狀態和版本。接受、拒絕、手動修正及撤銷均轉化為學習信號，但 LLM 不得直接發布規則。

### 11.3 回歸門檻

正式啟用前必須證明：

- 原有已確認標題不減少；
- 不新增正文誤標；
- 出生條目正文不被吞掉；
- 不新增年號、干支或年齡衝突；
- 新案例召回率確實提高；
- 正例和反例同時通過。

規則升級形成版本，記錄受影響案例並支持一鍵回退。

## 12. 通用文獻與未來擴展模型

第一版不把底層固定為「一部年譜包含若干年份」，而採用：

```text
ResearchCorpus
  └─ Work
      └─ SourceDocument
          └─ TemporalUnit[]
```

- `ResearchCorpus`：以一位人物或研究問題為中心的材料集合；
- `Work`：一部年譜、日記或其他作品；
- `SourceDocument`：具體版本、掃描本或 OCR 文件；
- `TemporalUnit`：帶時間範圍、原文和來源位置的最小引用單元。

第一版實現年譜 `YearEntry`；未來增加日記 `DiaryEntry`。二者共用 `TemporalUnit` 接口。

### 12.1 通用時間單元

```json
{
  "unit_id": "stable-id",
  "document_id": "source-id",
  "unit_type": "nianpu_year",
  "time": {
    "start_ad": 1582,
    "end_ad": 1582,
    "reign": "萬曆十年",
    "ganzhi": "壬午",
    "lunar_date": null
  },
  "subject_age": 48,
  "title_original": "...",
  "text_original": "...",
  "text_normalized": "...",
  "source_location": {
    "page": 17,
    "blocks": [],
    "line_range": []
  },
  "confidence": 0.97,
  "revision": 3
}
```

### 12.2 三層數據分離

1. 原始證據層：掃描、原始 OCR、原文及座標；
2. 整理層：標題、規範時間、整理稿及修正日誌；
3. 派生分析層：事件、人物、官職、著作、地點及跨文獻對齊。

派生層必須可重建。整理層變更時，相關派生數據標記過期，不刪除原始證據。

### 12.3 多視角文獻元數據

為本人日記、親友日記、門人記錄及後世年譜預留：

- `genre`；
- `author`；
- `focal_person`；
- `perspective`；
- `relation_to_focal_person`；
- `composition_time`；
- `event_time`；
- `edition`；
- `source_provenance`。

事件發生時間和文獻寫作時間必須分開。

### 12.4 未來抽取與對讀

未來抽取器讀取 `TemporalUnit`，輸出帶原文定位、抽取器版本、置信度和審核狀態的事件及實體。文本提及與消歧後實體分離。

年譜與日記先以時間重疊生成候選，再結合核心人物、地點、官職、著作及行為語義判斷是否為同一事件。對齊關係可為印證、補充、矛盾、疑似同一事件、無關或待核。矛盾只呈現證據，不由系統自動裁決史實真偽。

該比較可覆蓋：年譜與傳主本人日記、年譜與親友／門人／同時代人日記，以及本人日記與他人日記。

## 13. 錯誤處理與恢復

- 每個階段保存輸入、輸出、配置和工具版本；
- 任務可從指定階段恢復，不必整部重跑；
- OCR、CBDB 或 LLM 暫時失敗時記錄可重試錯誤，不破壞已有結果；
- 外部知識不可用時降級為本地錨點校驗；
- LLM 輸出不符合結構時重試一次，仍失敗則提交人工；
- 同一任務的處理版本彼此隔離；
- 所有自動修正和人工操作可撤銷；
- 批量任務中單部失敗不得阻塞其他年譜。

## 14. 測試與質量標準

### 14.1 測試層次

- 單元測試：中文數字、年號、公元年、干支、年齡和槽位轉換；
- 金標測試：逐條標記真實年份標題、非標題及來源位置；
- 序列測試：漏年、跳年、改元、無事年份及跨行標題；
- 負例測試：正文引用、序跋落款、註文日期、科舉小注及出生誤判；
- OCR 測試：原生文本、掃描、混合 PDF、豎排、雙欄和低品質頁；
- 回歸測試：既有成功年譜的標題數、覆蓋率和已知陷阱；
- 應用測試：批量任務、斷點恢復、審核、撤銷和導出；
- 契約測試：OCR、CBDB、LLM 和導出適配器。

### 14.2 核心指標

- 標題召回率；
- 標題精確率；
- 漏標數；
- 正文誤標數；
- 自動紀年修正錯誤數；
- 每部年譜人工核對比例；
- 局部重做 OCR 後解決的疑點數；
- 任務失敗恢復率；
- 規則升級後的回歸差異。

### 14.3 第一版驗收門檻

1. 已確認測試集中正文誤標新增數為零；
2. 所有自動修改均有至少兩個獨立證據；
3. 正文未經確認不被改寫；
4. 每個標題可追溯到原頁、原行和判斷依據；
5. 新規則未經回歸不得正式啟用；
6. 任務中斷後可恢復；
7. 每項修改可撤銷；
8. 新格式年譜可先生成任務級臨時槽位，不要求預寫專用正則；
9. 批量處理中每部年譜可獨立進入審核及導出。

## 15. 分階段交付

### P0：固化現有引擎

- 將 `nianpu_processor.py` 包裝為清晰的純函數接口；
- 將處理和檢查結果改為結構化數據；
- 建立年份標題金標集；
- 固化已有成功年譜的回歸基線。

驗收：相同輸入穩定產生相同結果，既有案例不回退。

### P1：接入與 OCR

- 批量導入；
- 文件及頁面級文字品質診斷；
- OCR 適配層；
- 頁面、行、版面框和文本映射；
- 任務進度及失敗重試。

驗收：可靠文本跳過 OCR，掃描件自動 OCR，混合 PDF 逐頁分流。

### P2：智能年份標題引擎

- 高召回候選生成；
- 臨時槽位歸納；
- 全譜序列求解；
- 正文紀年引用排除；
- 多錨點自動修正；
- 局部 LLM 仲裁與解釋。

驗收：新格式年譜不必先寫專用正則，既有語料不新增正文誤標。

### P3：審核工作區

- 原圖、OCR 和整理稿聯動；
- 年份時間線；
- 疑點篩選；
- 接受、拒絕、手動修正和撤銷；
- 單部 Markdown、報告和日誌導出。

驗收：使用者只處理疑點，不必通讀全部機器結果。

### P4：自然語言與受控學習

- 自然語言轉結構化任務；
- 候選槽位及規則生成；
- 正反例管理；
- 自動回歸；
- 規則發布、版本化及回退。

驗收：人工確認的新格式再次出現時可直接識別，失敗規則不能進入正式庫。

### P5：部署準備

- 配置與密鑰外置；
- 文件和數據庫備份；
- 任務資源限制；
- 基礎身份驗證；
- 容器化及部署文檔。

驗收：同一套核心服務可在本機和單服務器環境運行，資料可遷移和恢復。
