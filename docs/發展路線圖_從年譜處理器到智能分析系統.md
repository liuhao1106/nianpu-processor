# 發展路線圖：從「年譜處理器」到「智能分析系統」

> 版本：v1.0（草案）
> 日期：2026-08-06
> 定位：本文件是 `nianpu-processor`（及整套 OCR→整理 管线）演化為智能體／智能分析系統的總體方案。分三條路線詳述，並給出統一數據模型、分階段里程碑、技術選型與風險評估。**留存待用，非一次性執行文件。**

---

## 0. 現狀定位

### 0.1 目前已有的能力（不重複造輪子）

| 模組 | 能力 | 現有資產 |
|------|------|----------|
| 輸入 | PDF／掃描件／圖片 → Markdown | `paddleocr` skill（PaddleOCR-VL API） |
| 結構化 | 年份標題化、年號補全、公元標註 | `nianpu_processor.py` |
| 格式自適應 | L1 格式預分類、語義槽位配置 | `classify_format()`、`slot_model.py` |
| 自校 | L2 三錨點一致性檢查（年號年→公元、干支→公元、年齡→公元） | `--check`、`verify_anchors()` |
| 外部知識 | CBDB 生卒年核驗、年號誤配建議 | `cbdb.py`、`--cbdb`／`--fix` |
| 自我進化 | 學習新年號／字形／前綴／修正，存 learnings.json | L3 自我進化 |
| 質檢 | 覆蓋率、遺漏、年齡序列空缺報告 | 自動檢查報告 |
| RAG 評估 | 整理前後檢索效果對比 | `tools/nianpu_rag_compare.py` |
| 已處理語料 | 31 部年譜（含《許敬菴》53 條標題） | README 清單 |

### 0.2 三條關鍵躍遷（從「工具」到「系統」）

```
現在（規則管道）                    目標（智能分析系統）
─────────────────────             ─────────────────────
單文本處理                         語料庫級處理
調用者驅動（你叫它跑）             自主驅動（agent 循環）
規則引擎判定，歧義報錯             LLM 仲裁 + 人機協同
靜態 markdown 輸出                 結構化數據（事件/實體）
單部年譜                           跨譜知識圖譜 + 問答
人工校訂                           主動學習自動回灌
```

本方案以下列三條路線並行／接續推進，任一條可獨立啟動：

- **路線 A｜Agent 化**：把現有管道串成自主工作流，引入 LLM 仲裁與主動學習。
- **路線 B｜事件抽取（結構化）**：把每年正文結構化為「事件 + 實體」數據，是分析的物質基礎。
- **路線 C｜分析層**：知識圖譜、RAG 問答、跨譜對比、可視化、報告生成。

建議順序：**B（數據化）→ A（Agent 化）→ C（分析層）**。B 的數據模型會決定 A 與 C 的上限，故先定 B。

## 1. 路線 A：Agent 化 —— 從「工具」到「智能體」

### 1.1 目標

用戶只給一個 PDF（或文本），智能體自主跑完整條鏈並交付**結構化結果 + 校訂報告 + 待人工清單**，全程幾乎不需人工插手，遇歧義自動降級為「提出問題」。

### 1.2 總體工作流（一次完整執行）

```
[輸入] PDF / URL / txt / md
  │
  ▼
① 格式偵測 ────────────► 判類型：年譜？一般文獻？現代學者譜？圖表？
  │
  ▼
② OCR（如為掃描件）────► paddleocr → 逐頁 md + 完整檔
  │
  ▼
③ 年譜整理 ────────────► nianpu_processor.py（現有）
  │
  ▼
④ L2 三錨點自檢 ───────► 可疑清單 / 覆蓋率 / 年齡空缺
  │
  ├─ 全部通過 ──────────► ⑤
  └─ 有可疑/低置信度 ───► ⑥ LLM 仲裁器
                              ├─ 判定為 OCR/筆誤 ──► 自動修正 → 回④
                              ├─ 判定為新格式變體 ──► 產生新規則（回灌）→ 回④
                              └─ 置信度不足 ────────► 標 ⚠ 入「待人工清單」→ ⑤
  │
  ▼
⑤ 事件抽取 ────────────►（路線 B）每年 → 事件/實體 JSON
  │
  ▼
⑥ 入庫 ────────────────► SQLite/JSONL 語料庫（跨譜）
  │
  ▼
⑦ 交付 ────────────────► 已整理 md ＋ 結構化 json ＋ 校訂報告 ＋ 待人工清單
```

### 1.3 LLM 仲裁器設計（核心新組件）

**觸發時機**（滿足任一即進入仲裁）：
1. L2 三錨點不一致（如《許敬菴》尾部「二十七年庚子」vs 干支 1600）；
2. 規則引擎對年份匹配置信度 < 閾值；
3. 偵測到未收錄的年號／前綴／格式變體（L3 自我進化候選）；
4. 出生條目缺「生」動詞、正文首句疑似吞併等已知坑位。

**仲裁協議**（每案給 LLM 的上下文與期望輸出）：

```
輸入：{ 原文片段, 已識別錨點(年號年/干支/年齡/公元), 候選修正, 相關上下文 }
輸出：{ 決策: 修正|保留|待人工, 理由, 置信度(0-1), 新規則建議? }
```

**回灌機制**（把仲裁結果變成系統能力）：
- 確認為 OCR 誤 → 寫入 `learnings.json.corrections`（現有結構）；
- 確認為新格式 → 產生新的 pattern 或 slot 配置（`slot_model.py`）；
- 確認為稿本筆誤 → 記入「已知瑕疵」表，下次同類直接提示而非重仲裁；
- 連續 N 次同類仲裁 → 抽象為通用規則（主動學習，見 1.5）。

### 1.4 人機協同（HITL）

- 所有自動修正留**修正日誌**（改前/改後/依據/是否自動）；
- 不確定的統一標 `⚠` 並彙整為「待人工核對清單」（按影響度排序）；
- 提供 `--review` 模式：只輸出清單不落改，供人工確認後一鍵套用。

### 1.5 主動學習循環（從「記錄」到「自舉」）

現有 learnings.json 是**人工寫入**的靜態庫。升級目標：

```
每次處理
  │
  ├─ 規則命中但低置信度 ──► 仲裁 ──► 確定 ──► 生成/更新規則 ──┐
  ├─ 自檢發現異常        ──► 仲裁 ──► 確定 ──► 生成/更新修正 ──┤
  └─ 用戶事後人工修正    ──► 偵測 diff ──► 逆向生成規則 ────────┘
                                                              │
                                              ┌───────────────┘
                                              ▼
                                  規則庫（新增/驗證/去重/淘汰）
```

要點：
- 人工修正**自動捕捉**：比對用戶改後的檔案與輸出，差異自動轉為候選規則（附樣例），下次先用規則試跑。
- 規則**帶樣例**：每條規則存 2~5 個正反例，方便校驗與避免誤傷。
- 規則**有壽命**：多次無用的規則自動降級／標記，防止規則庫膨脹誤傷。

### 1.6 里程碑

| 階段 | 交付 | 驗收標準 |
|------|------|----------|
| A1 | 仲裁器原型（單案 CLI） | 對《許敬菴》已知 6 處問題全部給出正確決策 |
| A2 | 編排層（OCR→整理→仲裁→輸出一條龍） | 給 1 個新 PDF 全自動跑通 |
| A3 | 主動學習閉環 | 人工修正 1 次後，同類錯誤不再重犯 |
| A4 | HITL 清單 + `--review` | 新譜零人工干預率 > 80% |

## 2. 路線 B：事件抽取 —— 從「文本」到「數據」

### 2.1 目標

把每年正文抽取為**結構化事件 + 實體**，讓分析工具（路線 C）與問答有據可依。**這是整條路線的地基。**

### 2.2 統一數據模型（核心 Schema）

```
Nianpu（年譜）
 ├─ nianpu_id, 書名, 傳主, 傳主_cbdb_id, 生卒(公元), 卷數, 版本, OCR來源
 └─ YearEntry[]（年份條目）
     ├─ 年號年, 干支, 公元年, 傳主年齡, 標題, 正文原文
     └─ Event[]（事件）
         ├─ event_id, 類型(enum), 摘要, 時間(月/季/日), 地點
         ├─ 人物[]（含角色：主體/對象/師/友/僚屬）
         ├─ 官職[]（遷轉：除授→現任→遷→降）
         ├─ 著作[]（名稱 + 是否見集）
         └─ 原文引用 + 置信度 + 校訂註
```

**事件類型枚舉**（初期 10 類，可擴充）：

| 類型 | 說明 | 《許敬菴》示例 |
|------|------|----------------|
| 生卒 | 出生、卒、生辰 | 嘉靖十四年十一月二日生 |
| 仕宦 | 除授/遷/降/乞歸/復起 | 萬曆十一年陝西按察司提學副使 |
| 軍事 | 平亂、剿倭、撫寇、海防 | 隆慶五年雷州剿倭、撫李茂/許俊美 |
| 講學 | 會講、講學、門人問學 | 萬曆廿五年貢院會講（九諦之辨） |
| 著述 | 撰序/著書/刊刻 | 作《大學中庸述》、輯《左氏詳節》 |
| 交遊 | 訪友、送別、論學往返 | 會顧涇陽/高景逸論學 |
| 家庭 | 婚喪、生子、侍疾、守制 | 沈淑人病歿、孫元釗生、封公病 |
| 災荒 | 水旱災、賑濟、度田 | 督煮糜濟饑、靈雨頌 |
| 政論 | 上疏、條陳、議政 | 陳馬政四策、請勅諭日本 |
| 行誼 | 德行、日常生活 | 元旦常活人於大澤中 |

### 2.3 實體識別

| 實體 | 來源 | 對接 |
|------|------|------|
| 人物 | 正文人名 + 稱謂（公/先生/翁/名） | CBDB 匹配（`cbdb.py`），帶 id 與生卒 |
| 地點 | 州府縣/山川書院（德清、雷州、建昌、峴山…） | 地名庫或地圖 geocoding |
| 官職 | 官名詞表（提學副使/兵部侍郎/僉都御史…） | 明清職官表 |
| 著作 | 「《X》」「X序」「見集」模式 | 書目 |
| 師承/交遊 | 語義關係（受學、執贄、往還、論學） | 關係抽取 |

### 2.4 抽取方法（規則 + LLM 兩段式）

1. **規則預抽取**（現有工具擅長、免費、確定）：
   - 標題層：年號年/干支/公元/年齡（已 100% 可靠）；
   - 正文層：官職遷轉詞表、著作「見集」模式、時間詞（春/夏/秋/冬/月/日）、人物稱謂。
2. **LLM 精標**（對規則無法確定的片段）：
   - 給 LLM：當年正文 + 已抽取的錨點 + schema；
   - 輸出：事件 JSON + 置信度；
   - 抽樣人工覆核，統計準確率。
3. **一致性校驗**：事件時間必須落在所屬 YearEntry 的年份內，越界即報錯（防止「跨年句子」被切錯）。

### 2.5 輸出

- `data/許敬菴先生年譜.jsonl`（每行一年）
- `data/nianpu.db`（SQLite：nianpu / year / event / entity 四表）
- 每年事件可匯出為 Markdown 附表（便於人讀校對）

### 2.6 里程碑

| 階段 | 交付 | 驗收標準 |
|------|------|----------|
| B1 | 定 schema + 註標工具 | 10 年人工標註樣例，前後一致 |
| B2 | 規則預抽取 | 《許敬菴》53 年官職/著作/時間詞召回率 > 85% |
| B3 | LLM 精標管線 | 53 年全部結構化，抽樣準確率 > 90% |
| B4 | 批量：31 部年譜全部入庫 | 語料庫覆蓋全部已處理年譜 |

## 3. 路線 C：分析層 —— 從「單譜」到「系統」

### 3.1 知識圖譜（對接 graphify）

**節點**：人物（含 CBDB id）、地點、官職、著作、事件、年譜。

**關係**（有向，含時間戳）：

| 關係 | 示例 |
|------|------|
| 師承/受學 | 許孚遠 —受學→ 唐樞 |
| 執贄/門生 | 馮從吾、劉宗周、丁元薦 —師從→ 許孚遠 |
| 交遊/論學 | 許孚遠 —論學↔ 顧憲成、高攀龍 |
| 任職 | 許孚遠 —任→ 福建巡撫（1582-1585） |
| 徙居/宦遊 | 許孚遠 —居→ 德清、建昌、雷州… |
| 著書 | 許孚遠 —著→ 《大學中庸述》《易義》 |
| 論戰/思想 | 許孚遠 —著《九諦》難→ 周汝登「無善無惡」說 |

**跨譜價值**：《許敬菴》的唐樞、羅汝芳、高攀龍、劉宗周**同時出現在其他年譜**（如《唐一庵先生年譜》《蕺山先生年譜》），圖譜能把分散語料連成一個晚明思想網絡。

### 3.2 RAG 問答

- 分塊策略：以 YearEntry 為天然 chunk（每塊 < 800 字，含元數據），避免句子切半；
- 檢索：BM25（現有 `nianpu_rag_compare` 基礎）＋向量混合（hybrid）；
- 過濾：按年號年/公元/人物/事件類型做結構化過濾後再檢索；
- 問答範例：
  - 「許孚遠哪一年任福建巡撫？」（結構化直查）
  - 「許孚遠與顧憲成何時論學？談了什麼？」（檢索 + 摘要）
  - 「許孚遠一生貶謫過幾次？都在哪幾年？」（跨年聚合）

### 3.3 跨譜對比分析

- **同年齡對照**：多位傳主 N 歲時的狀態（入仕/講學/著述）；
- **同年號橫切**：某一年號下各譜事件並置（如萬曆年間各傳主動向）；
- **人物共現**：兩譜共同人物 → 關係網補全；
- **仕途/地域軌跡**：升遷序列、宦遊地圖（可視化）。

### 3.4 報告生成

- 傳主分析報告模板：生平簡表 → 仕途時間線 → 講學/著述年表 → 交遊網絡 → 思想關鍵論辨 → 疑點與文獻校訂記錄；
- 可匯出 Markdown / HTML / PDF。

### 3.5 里程碑

| 階段 | 交付 | 驗收標準 |
|------|------|----------|
| C1 | 語料庫查詢 API（時間/人物/類型過濾） | 《許敬菴》全部年份可程式化查詢 |
| C2 | 知識圖譜（graphify 對接） | 5 部年譜建圖，人物/關係可視 |
| C3 | RAG 問答 | 10 個標準問答準確率 > 85% |
| C4 | 跨譜對比 + 報告 | 產出一份《許孚遠》分析報告樣張 |

## 4. 統一技術架構

```
┌─────────────────────────────────────────────────────────────┐
│  接入層：/nianpu 命令、CLI、未來 Web/API                       │
├─────────────────────────────────────────────────────────────┤
│  智能體層（路線A）                                            │
│  編排器(agent loop) ─ LLM仲裁器 ─ HITL清單 ─ 主動學習器        │
├─────────────────────────────────────────────────────────────┤
│  領域引擎                                                     │
│  nianpu_processor.py ─ cbdb.py ─ slot_model.py ─ 事件抽取器   │
├─────────────────────────────────────────────────────────────┤
│  數據層（路線B）                                              │
│  learnings.json ─ 規則庫 ─ data/nianpu.db(SQLite) ─ 修正日誌   │
├─────────────────────────────────────────────────────────────┤
│  分析層（路線C）                                              │
│  graphify圖譜 ─ RAG檢索/問答 ─ 對比分析 ─ 報告生成             │
├─────────────────────────────────────────────────────────────┤
│  輸入：paddleocr（PDF→md）／既有 _完整.md／_已整理.md          │
└─────────────────────────────────────────────────────────────┘
```

**技術選型**：

| 層 | 選型 | 理由 |
|----|------|------|
| 語言/執行 | Python | 現有全部資產為 Python |
| 儲存 | SQLite + JSONL | 單機、零依賴、可版本化 |
| LLM | Claude API（模型可換） | 文言理解強，仲裁/抽取均需 |
| 圖譜 | graphify（既有 skill） | 不另造輪子 |
| 檢索 | BM25 + 向量 hybrid | 文言分詞難，混合最穩 |
| 校訂 | git（檔案層）＋修正日誌 | 可回溯、可復原 |

## 6. 分階段總路線圖

| 階段 | 內容 | 前置 | 產出 | 建議時長 |
|------|------|------|------|----------|
| **P0 現況固化** | 整理現有能力、定 schema、定規則庫格式 | — | 本文檔 + schema 文件 | 1 天 |
| **P1 數據化（路線B）** | B1→B2→B3→B4，《許敬菴》先做 | P0 | 語料庫 db + 標註規範 | 1~2 週 |
| **P2 Agent化（路線A）** | A1→A2→A3→A4 | P1（有結構化後仲裁更好做） | 自主 pipeline | 1~2 週 |
| **P3 圖譜（路線C-1）** | graphify 對接、5 部建圖 | P1 | 人物關係網絡 | 1 週 |
| **P4 問答/對比/報告（路線C-2）** | RAG、跨譜、報告模板 | P1+P2+P3 | 分析工作台 | 1~2 週 |

> 里程碑以「每階段有可驗收成果」為準；P1 與 P2 可微並行，但**事件 schema 必須先定**，否則後續重構成本高。

## 7. 風險與注意事項

| 風險 | 影響 | 緩解 |
|------|------|------|
| OCR 誤差傳導 | 事件抽取把錯字當真 | 抽取前先做正文規範化（己/已/巳 等）；事件附原文引用可回溯 |
| 稿本特有筆誤 | 年序錯位、漏字、異體 | 以干支/年齡/CBDB 錨點校正；記入「已知瑕疵」表 |
| 古文無句讀 | 分句/事件邊界難定 | 依「標題-正文」結構 + 季節/月/日標記定界；抽樣人工覆核 |
| LLM 成本 | 仲裁/抽取大量調用 | 規則優先、LLM 兜底；快取（已有 cbdb_cache 模式可複用） |
| 標註一致性 | 兩次抽取同事件結果不一 | 明確 schema 與範例、覆核抽樣、一致性校驗（時間越界報錯） |
| 規則庫膨脹 | 誤傷正文 | 規則帶樣例、帶壽命、去重淘汰（L3 現有機制擴展） |
| 隱私/許可 | 語料來自掃描古籍 | 僅本地處理，輸出保留來源標記 |
